Database tracking

Thiết kế 2 bảng mới

econtract_transactions (bảng A)

Trạng thái hiện tại của một luồng xử lý.

  • guid
  • template_id
  • contract_no
  • phone
  • step: OPEN / UPDATE_ID / VERIFICATING / VERIFIED / SIGNED
  • initial_verification_type: OTP / VNEID / NONE
  • verification_type: OTP / VNEID / NONE
  • verification_status: PENDING / SUCCESS / FAILED
  • platform: WEB / APP
1 → N

econtract_tracking (bảng B)

Lịch sử hành động và dữ liệu phát sinh.

  • econtract_transaction_id
  • step: Xem Biên bản / Cập nhật CCCD / Xác thực OTP / Xác thực VNEID / By pass OTP / Xác thực thành công / Đổi phương thức xác thực / Xác thực lỗi / Ký thành công...
  • date_action
  • data: JSON/text snapshot (lưu thông tin lấy từ 3rd check điều kiện vneid, lưu thông tin tạo transaction vneid, xác thực, thông tin by pass OTP, ...)
Mapping database

Mỗi bước xử lý ghi nhận như thế nào?

Luồng econtract_transactions econtract_tracking
Mở view Nếu chưa có row: tạo step = OPEN Insert step = Xem biên bản, platform = WEB / APP
Cập nhật CCCD step = UPDATE_ID Insert step = Cập nhật CCCD, data : idCard
Mở OTP step = VERIFICATING, verification_type = OTP Insert step = OTP_SEND / OTP_ACTIVE
OTP thành công step = VERIFIED, verification_status = SUCCESS Insert step = OTP_SUCCESS
Mở VNEID step = VERIFICATING, verification_type = VNEID Insert transactionLink, transactionCode, status
Check verification success true → VERIFIED, false → VERIFICATING Insert step = Tình trạng xác thực, data từ 3rd
Ký thành công step = SIGNED Insert step = Kí thành công, platform = WEB / APP
Case phát sinh

Cách xử lý các tình huống thay đổi giữa luồng

Bypass

Nhân viên chuyển VNEID → OTP

  • Update bảng A: verification_type = OTP.
  • Insert bảng B: By pass OTP.
  • Ghi rõ người thao tác và thời điểm.
3rd changed

Dữ liệu ISC/SPF thay đổi

  • So sánh dữ liệu hiện tại với dữ liệu đã lưu.
  • Insert bảng B: Có thay đổi giá trị từ 3rd.
  • Update verification_type nếu rule thay đổi.
VNEID failed

VNEID thất bại

  • Map đúng failed case.
  • Update bảng A: verification_status = FAILED.
  • Insert bảng B với raw response cần thiết.

Kết luận

Nguyên tắc chốt khi triển khai

Nguyên tắc API

  • view chỉ xem.
  • view-action chỉ điều hướng.
  • update_id_card v2 chỉ cập nhật CCCD.
  • check-verification chỉ kiểm tra điều kiện xác thực.
  • vneid-status chỉ xử lý xác thực VNEID
  • otp-active chỉ xử lý xác thực OTP
  • sign chỉ ký.

Nguyên tắc Database

  • econtract_transactions là trạng thái hiện tại.
  • econtract_tracking là lịch sử xử lý.
  • Trong giai đoạn đầu, ghi song song với table cũ.
  • Khi ổn định, chỉ lưu ở bảng mới.
Sau refactor, khi cần debug một hợp đồng, chỉ cần xem transaction hiện tại và tracking timeline là biết khách hàng đang đứng ở bước nào, lỗi ở đâu và API nào đã xử lý.
